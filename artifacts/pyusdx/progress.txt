  - Validation: Rate cannot exceed 100% (PRECISION = 1e12)
  - Updates index to apply old rate for elapsed period before setting new rate

**Gotchas:**
- The validation formula `newRate > 10000 * uint32(PRECISION)` overflows because `10000 * 1e12 = 1e16` exceeds `uint32` max (~4.3e9)
- Fixed by using `newRate > uint32(PRECISION)` instead, since the rate format is `bps * PRECISION / 10000`, so 100% = 1e12
- Test rate calculations needed to use `uint256` casting to avoid overflow during test compilation: `uint32((uint256(1000) * uint256(PRECISION)) / 10000)`
- Rate format: rate is stored as `bps * PRECISION / 10000`, so 10% = 1000 * 1e12 / 10000 = 1e11

- Note: PYUSDX implements these functions internally using custom storage layout (via `IndexingState` struct in `PYUSDXStorageStruct`) instead of inheriting from ContinuousIndexing
- Unit tests cover:
  - UpdateIndex: Cache behavior, rate=0 (no growth), rate>0 with time (growth + IndexUpdated event), rate changes (compounding)
  - CurrentIndex: Returns latestIndex immediately after update, calculates growth with time elapsed, no growth when rate=0 or no time passed, monotonicity (never decreases)
- Tests are executed indirectly via `setRate` (which calls `_updateIndex()`) and `currentIndex()` view function

**Gotchas:**
- Rate format for ContinuousIndexingMath.getContinuousIndex is a raw uint32 value, not `bps * PRECISION / 10000`
- Rate values that fit in uint32: ~1.2% APY uses rate value ~1.2e9 (1215752192)
- Rate calculation `bps * PRECISION / 10000` overflows for most common values since `1e11 > 2^32`
- Solution: Use raw uint32 values directly that are compatible with ContinuousIndexingMath
- Index growth is small (~1.2% annually for rate=1215752192), so tests check for positive growth rather than specific percentages
- Used `vm.warp()` to simulate time passage for index growth tests

=== Phase 2.7: Accrued Yield Calculation ===

COMPLETED: accruedYieldOf function implementation

Implementation:
- Added accruedYieldOf(address) external view function
  - Returns 0 for non-earners (checks isEarning flag)
  - Calculates balance with yield: earningPrincipal × currentIndex / PRECISION
  - Returns difference: max(0, balanceWithYield - balance)
  - Uses IndexingMath.getPresentAmountRoundedDown for calculation

- Added _getAccruedYield internal helper (pure function)
  - Encapsulates yield calculation logic for reuse
  - Handles edge case: zero principal returns 0
  - Safe subtraction: returns 0 if balanceWithYield <= balance

Tests Added:
- test_AccruedYieldOf_AccountNotEarning_ReturnsZero: Verifies 0 for non-earners
- test_AccruedYieldOf_IndexEqualsPrecision_NoGrowth_ReturnsZero: Verifies 0 when no index growth
- Additional tests deferred to Phase 2.9 (require startEarningFor to properly set up earner state)

Gotchas:
- The IndexingMath.getPresentAmountRoundedDown function expects (principal, index) and returns the present value
- The formula is: balanceWithYield = principal × index / PRECISION (rounded down)
- Yield is then: balanceWithYield - balance (capped at 0)
- Non-earners always return 0 regardless of balance or index

#### Phase 2.9: Start Earning For
**Status:** COMPLETED

**Approach:**
- Implemented `startEarningFor(address account)` function:
  - Permissionless function (anyone can call for any approved earner)
  - Pre-flight checks: Not paused, account not frozen, account is whitelisted as earner, not already earning
  - Principal calculation: `balance × PRECISION / currentIndex` using `IndexingMath.getPrincipalAmountRoundedUp`
  - Sets `isEarning = true`, stores `earningPrincipal`
  - Updates `totalEarningPrincipal`, `totalEarningSupply`, `totalNonEarningSupply`
  - Calls `_updateIndex()` at end
  - Emits `StartedEarning(account)` event

- Implemented `startEarningFor(address[] calldata accounts)` batch variant:
  - Loops through accounts and applies same logic as single variant
  - Skips non-approved and already-earning accounts (continues instead of reverting)
  - Validates array length > 0
  - Emits `StartedEarning` event for each successfully started account

- Added `totalEarningPrincipal()` view function for testing

- Unit tests cover:
  - Not approved earner reverts
  - Paused contract reverts (with `whenNotPaused` modifier check)
  - Frozen account reverts (with `_revertIfFrozen` check)
  - Already earning reverts
  - Zero balance: success with isEarning=true, earningPrincipal=0
  - Positive balance: success with proper principal calculation, supply tracking updates
  - Batch with multiple accounts: all marked as earning
  - Batch with empty array: reverts
  - Batch with mix of approved/non-approved: only approved start earning

**Gotchas:**
- The batch variant uses `continue` for non-approved or already-earning accounts instead of reverting

- Principal calculation uses `getPrincipalAmountRoundedUp` to ensure users don't lose yield due to rounding
