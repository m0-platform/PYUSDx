## 1. Overview

### 1.1 Problem Statement

Institutional and regulated DeFi participants need access to yield on their stablecoin holdings without requiring direct interaction with underlying yield sources (e.g., Treasury bills, money market funds). Traditional yield-bearing tokens require users to wrap or deposit their tokens, creating friction and custody concerns. Additionally, regulated use cases require compliance features like freezing, forced transfers, and pausing capabilities.

### 1.2 Proposed Solution

PYUSDX is an upgradeable, non-rebasing ERC20 token that represents claim on PYUSD collateral held by a custodial minter. Users receive PYUSDX without wrapping their PYUSD directly - the minter holds PYUSD in custody and mints PYUSDX 1:1. Yield accrues via an ever-increasing index that tracks off-chain yield from external financial instruments (e.g., T-bills). Yield must be explicitly claimed by token holders, and the protocol supports optional fee collection on yield via an Earner Manager system.

### 1.3 Success Criteria

- Users can hold PYUSDX tokens that track PYUSD value
- Approved earners can accrue yield based on an ever-increasing index
- Yield is claimable and can be redirected to custom recipients
- Protocol has built-in compliance: freezing, forced transfers, and pausing
- System supports optional fee collection on yield
- All operations are gas-efficient and secure

## 2. Background & Context

### 2.1 Current State

The project is a greenfield implementation. Foundry project structure exists with placeholder contracts. The technical specifications for both PYUSDX and EarnerManager have been defined.

### 2.2 Strategic Fit

PYUSDX is part of the M0 ecosystem, providing regulated institutions with a compliant yield-bearing stablecoin option. It integrates with M0's common libraries and follows established patterns from wrapped-m-token.

### 2.3 Prior Art & Research

- **Wrapped M Token**: Reference implementation for non-rebasing tokens with claimable yield
- **M0 Protocol**: Continuous indexing pattern for yield accrual
- **ERC-2612**: Permit standard for gasless approvals
- **ERC-3009**: Gasless transfers via EIP-712 signatures

## 3. User Stories & Actors

### 3.1 Actors

| Actor           | Description |
| --------------- | ----------- |
| **Token Holder** | Holds PYUSDX tokens, may be an earner or non-earner |
| **Earner**      | Token holder approved to earn yield on their balance |
| **Admin**       | Protocol administrator with DEFAULT_ADMIN_ROLE |
| **Earner Manager** | Address authorized to approve/remove earners and set fee rates |
| **Freeze Manager** | Address authorized to freeze/unfreeze accounts |
| **Forced Transfer Manager** | Address authorized to force transfer from frozen accounts |
| **Pauser**      | Address authorized to pause/unpause contract operations |
| **Minter Gateway** | External contract authorized to mint/burn PYUSDX |

### 3.2 User Stories

#### US-1: Receive PYUSDX Tokens

**As a** Token Holder
**I want to** receive PYUSDX tokens from the Minter Gateway
**So that** I can hold a token representing claim on PYUSD collateral

**Acceptance Criteria:**
- [ ] Minter Gateway can mint PYUSDX to my address
- [ ] Minted tokens are reflected in my balance
- [ ] Minting is rejected if my account (recipient) is frozen
- [ ] Minting is rejected if contract is paused

#### US-2: Earn Yield on My Tokens

**As a** Token Holder
**I want to** be approved as an earner
**So that** my PYUSDX balance accrues yield over time

**Acceptance Criteria:**
- [ ] Earner Manager can approve me as an earner
- [ ] Once approved, my balance starts earning yield
- [ ] My earning principal is recorded when I start earning
- [ ] I cannot start earning if I'm frozen
- [ ] I cannot start earning if contract is paused

#### US-3: Claim Accrued Yield

**As an** Earner
**I want to** claim my accrued yield
**So that** I receive the yield generated by my tokens

**Acceptance Criteria:**
- [ ] I can call claimFor to receive my yield
- [ ] Anyone can call claimFor on my behalf
- [ ] Claiming mints new tokens to my balance
- [ ] My earning principal stays the same after claiming
- [ ] Cannot claim if I'm not earning or if yield is zero

#### US-4: Redirect Yield to Another Address

**As an** Earner
**I want to** set a custom claim recipient
**So that** my yield goes to a different address (e.g., treasury, fee recipient)

**Acceptance Criteria:**
- [ ] Earner Manager can set a custom claim recipient for me
- [ ] Yield claims go to the custom recipient instead of me
- [ ] By default, if no claim recipient is set, yield goes to me (the earner)
- [ ] To clear a custom recipient, Earner Manager calls setClaimRecipient(account, account)
- [ ] Only Earner Manager can set claim recipients (users cannot set their own)

#### US-5: Stop Earning Yield

**As an** Earner
**I want to** stop earning yield
**So that** I can opt out of the yield program

**Acceptance Criteria:**
- [ ] Earner Manager can remove me as an earner
- [ ] Any unclaimed yield is automatically claimed when I stop earning
- [ ] My balance moves from earning to non-earning supply
- [ ] I no longer accrue yield after stopping

#### US-6: Transfer Tokens

**As a** Token Holder
**I want to** transfer my PYUSDX to another address
**So that** I can make payments or move my tokens

**Acceptance Criteria:**
- [ ] Standard ERC20 transfer works
- [ ] Transfer respects freeze status of both sender and recipient
- [ ] transferFrom also respects freeze status of msg.sender (the spender)
- [ ] Transfer respects pause status
- [ ] Earning principals update when transferring between earners
- [ ] Supply tracking updates when transferring between earners and non-earners

#### US-7: Pay Fees on Yield

**As an** Earner with fee rate set
**I want to** have fees deducted from my yield
**So that** a portion goes to the protocol/manager

**Acceptance Criteria:**
- [ ] Earner Manager can set a fee rate (0-100%) on my account
- [ ] When claiming yield, fees are deducted automatically
- [ ] Fee portion goes to fee recipient
- [ ] Net yield goes to my claim recipient
- [ ] Cannot set fee > 100%

#### US-8: Emergency Freeze

**As a** Freeze Manager
**I want to** freeze a suspicious account
**So that** prohibited activity can be blocked

**Acceptance Criteria:**
- [ ] Can freeze any account
- [ ] Frozen accounts cannot transfer, mint, burn, or claim
- [ ] Can unfreeze frozen accounts
- [ ] Freezing emits an event for tracking

#### US-9: Emergency Pause

**As a** Pauser
**I want to** pause the entire contract
**So that** no operations can occur during emergency

**Acceptance Criteria:**
- [ ] Can pause all contract operations
- [ ] Paused state blocks transfers, mints, burns, claims
- [ ] Can unpause to restore operations
- [ ] Pausing emits an event

#### US-10: Forced Transfer from Frozen Account

**As a** Forced Transfer Manager
**I want to** transfer tokens from a frozen account
**So that** funds can be recovered from prohibited actors

**Acceptance Criteria:**
- [ ] Can force transfer from frozen accounts
- [ ] Can specify recipient of forced transfer
- [ ] Cannot force transfer from non-frozen accounts
- [ ] Emits event for transparency

#### US-11: Set Yield Rate

**As a** Minter Gateway
**I want to** set a new yield rate on the RateModel contract
**So that** PYUSDX earners receive yield at the correct rate

**Acceptance Criteria:**
- [ ] Can call setRate(newRate) on RateModel
- [ ] Rate must be valid (0-100%)
- [ ] Next updateIndex() call in PYUSDX will fetch and apply the new rate
- [ ] Emits event when rate changes

## 4. Functional Requirements

### 4.1 Core Functionality

#### FR-1: Token Operations

**Priority:** Must Have
**Description:** PYUSDX must implement standard ERC20 operations (transfer, transferFrom, approve, balanceOf, totalSupply) with additional freezing and pausing checks.
**Rationale:** Basic token functionality is required for any ERC20 token to be useful.

#### FR-2: Mint and Burn via Minter Gateway

**Priority:** Must Have
**Description:** Only the Minter Gateway contract can mint and burn PYUSDX tokens. Mint/burn must respect pause and freeze states.
**Rationale:** Ensures controlled supply based on PYUSD collateral held by minter.

#### FR-3: Yield Accrual via Index

**Priority:** Must Have
**Description:** Yield accrues via an ever-increasing global index. Each earner's principal balance is stored separately from their total balance. To calculate accrued yield: `(principal × currentIndex / PRECISION) - currentBalance`. The balance including accrued (but unclaimed) yield is: `principal × currentIndex / PRECISION`.
**Rationale:** Non-rebasing approach stores a single principal per user and calculates yield on-demand using the global index.

#### FR-4: Explicit Yield Claiming

**Priority:** Must Have
**Description:** Yield must be explicitly claimed by calling claimFor. It does not auto-claim or auto-compound.
**Rationale:** Gives users control over when they recognize yield and associated gas costs.

#### FR-5: Index Update via RateModel

**Priority:** Must Have
**Description:** PYUSDX calls updateIndex() which fetches the current rate from the RateModel contract. If the fetched rate differs from the stored latestRate, PYUSDX updates its rate. Minter Gateway calls setRate(newRate) on RateModel to change the rate.
**Rationale:** Separates rate storage (RateModel) from index calculations (PYUSDX).

#### FR-6: Earner Approval System

**Priority:** Must Have
**Description:** Only addresses approved by Earner Manager can earn yield. Non-approved holders hold tokens but earn no yield.
**Rationale:** Compliance requirement - not all token holders may be eligible for yield.

#### 4.2.2 Access Control

| Function/Action           | Permitted Actors                    | Conditions                       |
| ------------------------- | ----------------------------------- | -------------------------------- |
| Mint/Burn                 | Minter Gateway only                 | Not paused, account not frozen   |
| Start earning             | Token holder (triggered by anyone) | Not frozen, approved by Earner Manager |
| Stop earning              | Token holder (triggered by anyone) | Approved removal by Earner Manager |
| Claim yield               | Anyone (on behalf of earner)        | Not paused, account not frozen, earner has yield |
| Set claim recipient       | Earner Manager only                 | Account is earning               |

| Pause/unpause             | Pauser only                         | -                                |

| Set rate (on RateModel)   | Minter Gateway only                | New rate is valid (0-100%)         |

## 5. Non-Functional Requirements

### 5.1 Security Requirements

- All role-based operations must validate caller permissions
- Integer overflow/underflow protection (Solidity 0.8+)
- Zero address checks on all critical address parameters
- Time-based calculations must handle timestamp edge cases
- Upgradeability must follow Transparent Proxy pattern

### 5.2 Performance Requirements

- Single claim operation should cost < 200k gas
- Transfer operations should cost < 100k gas
- Batch operations for earners should handle at least 100 accounts per transaction

### 5.3 Upgrade & Migration

- Contract is upgradeable via Transparent Proxy pattern
- Upgrades must preserve all state
- No state migration planned for v1

## 6. Constraints & Assumptions

### 6.1 Constraints

- Yield source is off-chain (e.g., T-bills) - rate must be manually updated
- Index increases monotonically - cannot decrease
- Token cannot go below 1:1 peg with PYUSD in normal operation
- Fee rates are limited to 100% maximum
- Solidity version 0.8.30 required
- No cap on total earning supply

### 6.2 Assumptions

- Minter Gateway is a trusted custodian holding PYUSD 1:1 with PYUSDX supply
- Minter Gateway calls setRate(newRate) on RateModel to change the yield rate
- PYUSDX calls updateIndex() which reads from RateModel and updates internal rate if changed
- Index accrues continuously based on the rate from RateModel
- Earner Manager will properly vet and approve eligible earners
- Removing earners has no delay/queue; takes effect immediately
- Freeze/Pauser roles are held by reputable governance
- Off-chain yield assets are secure and generate expected returns

## 7. Anti-Goals (Out of Scope)

**The following are explicitly NOT part of this feature:**

- **Automatic yield compounding**: Yield must be explicitly claimed, no auto-compound
- **On-chain yield tracking**: Yield source is off-chain, only rate/index is tracked
- **Registrar support**: Earner status is managed by EarnerManager only, not via registrar
- **Migratable pattern**: Uses standard OpenZeppelin upgradeable, not custom migration
- **Staking or locking**: No lock-up periods or staking requirements
- **Governance**: No on-chain governance for parameter changes (admin-controlled)
- **Flash loans**: Not a lending protocol, no flash loan support
- **Rebasing**: Token is non-rebasing, balances don't auto-adjust with yield

## Appendix

### A. Glossary

| Term           | Definition                                                               |
| -------------- | ------------------------------------------------------------------------ |
| **PYUSD**      | PayPal USD stablecoin                                                    |
| **PYUSDX**     | Yield-bearing ERC20 token backed by PYUSD collateral                      |
| **Earner**     | Token holder approved to receive yield                                   |
| **RateModel**  | Contract that stores the current yield rate; Minter Gateway calls setRate() to update it |
| **Index**      | Global increasing value representing cumulative yield multiplier. Current balance = principal × index / PRECISION |
| **Principal**  | Original balance amount stored separately from total balance. Used for yield calculations and does NOT include claimed yield |
| **Claim Recipient** | Address that receives claimed yield (may differ from earner)        |
| **Rate**       | Yield rate (e.g., 4% annual) stored in RateModel, fetched by PYUSDX on updateIndex() |
| **Non-rebasing** | Token balances don't auto-adjust with index; principal stays constant, yield is claimed separately |
